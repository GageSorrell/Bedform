# Cinnabar automation contract v1

`Model.mjs` owns the schema and the operation, event, and action registries. The generated [Draft 7 schema](automation-v1.schema.json) describes the JSON messages and document formats. The TypeScript binding contains readonly wire shapes and constants. Rust, Go, and C++ use their generated constants and the same JSON schema. The `x-operation-receivers` annotation specifies which endpoint can receive each operation. Every request and success response has a matching operation discriminator and operation-specific shape.

## Transport and compatibility

- Control uses `POST /automation/v1` with a UTF-8 JSON message and `Authorization: Bearer <token>`. Bind the listener to `127.0.0.1`. Use a 256-bit random token encoded as lowercase hexadecimal for each authorized peer. Store discovery details in a `ControlEndpoint` document in a private, account- or module-scoped location. Protect it with the corresponding Windows ACL or private server-admin configuration. Redact credentials from all diagnostics, events, receipts, and manifests.
- A peer first sends `Hello`; verify its role and compare the entire compatibility tuple against the locally installed manifest before enabling any other operation. The `compatibilitySha256` is the SHA-256 of the exact installed `compatibility.json` bytes. The host receives script and provisioning requests and calls bridge and renderer endpoints as `host`. The provisioner may use only `Hello` and `Capabilities`. The host's stdio MCP adapter uses the same request types and authorization scope internally. Existing renderer developer-control clients retain their upstream protocol. The host can adapt the private renderer endpoint to that interface. The automation endpoint and renderer endpoint each have independent credentials.
- Capabilities describe the authenticated endpoint. Validate UTF-8, JSON, envelope version, operation payload, size and numeric ranges before scheduling work. Use the generated `ControlBytes` limit in both directions. Correlate responses by request ID and, for known operations, by operation. Use an HTTP 200 response with the typed result for correlatable requests. Malformed or oversized uncorrelatable requests may receive HTTP 400 or 413 without a response envelope. Bound response messages, timeouts and event pages. A client's timeout uses host elapsed time from acceptance, including queue delay. Expired commands may not start. If work already started, cancel where possible and allow inspection of its recorded outcome. Reject duplicate IDs on the same credential while in flight. Use new IDs to inspect or send new work after timeout.
- Events are ordered per credential by positive `sequence`. `PollEvents` starts at `after: 0`, returns events with sequence greater than `after`, and gives the last delivered sequence as `next`. An empty page leaves the cursor unchanged. Session filters are scoped to the exact session handle. On a cursor that has fallen out of the bounded event buffer, return `ResourceLimit` and let the caller recover state from `State`, `ListTriggers`, and `Artifacts`. Terminal state and finalized artifact results remain available for their owning run. MCP diagnostic text goes to stderr; scripts and MCP consume event envelopes.
- Use finite JSON numbers. Safe integer fields deliberately stop at JavaScript's safe-integer limit. Entity IDs use signed 64-bit decimal strings and runtime IDs use unsigned 64-bit decimal strings. Reject out-of-range strings on decode as well as noncanonical spellings. Never derive a persisted identity from a native pointer. The selected tuple comes from [compatibility.json](../compatibility.json) and the BDS build from the [exact-player feasibility evidence](../Native/README.md). The evidence covers both spawn APIs and visible Windows desktop captures. The internal PNG readback remained black in that proof.

## Sessions and packet routing

- `Attach` resolves the already-spawned native simulated player on the BDS thread. `Player` is an identity snapshot taken at attach. `(serverInstanceId, entityId)` identifies the native player for a server process. A complete `Session` is an immutable authority reference. `SessionState.runtimeId` reports the latest runtime ID after transitions. Allocate a fresh session ID and increment its per-player generation on reattach. Validate the entire handle and authorized caller before access. Reject duplicate attachments. Scope player observations, renderer instances, and input to one handle. Hidden is the default and `visible` is opt-in.
- The bridge `Attach` success includes `packets`; the host consumes this field privately. On bridge → host, use the existing [Cinnabar session wire](../../crates/protocol/src/session_wire.rs) and [Go session framing](../../core/proxy/session_messages.go). The per-attach listener is loopback. Its first host → bridge frame is `PacketBind` JSON, prefixed by a four-byte big-endian payload length. The bridge compares the complete handle and one-time token and consumes the token on success. Start the bridge stream with the existing `Handoff` frame carrying the actual player identity, startup packets through `StartGame`, and pack metadata. Deliver `PackData`, `Batch`, and terminal `Disconnect` in the existing order and framing. The host adapts this stream to the renderer's existing `Connect` handshake and leaves renderer `Batch` transactions intact. A relay may forward unknown, well-formed outgoing game packets unchanged within the pinned protocol. Preserve recipient scope for targeted and per-dimension broadcasts.
- On the native ingress socket after bind, frame each payload as `u32be metadata length | UTF-8 PacketIngress JSON | Cinnabar Batch payload`. Prefix that payload with the same four-byte frame length as the handoff. Limit metadata to `ControlBytes` and the complete frame to the existing session maximum. The host tags each batch with the lease active when the input was accepted. Check session generation and lease at dispatch on the server thread, including after queue delay. Supply the optional lease for player-mutating packets. Allow lease-free packets only for explicitly recognized bootstrap and non-mutating protocol replies. Render focus, inventory, and form actions travel through ordinary client input and player packet handling.
- A session can transition `attaching → ready ↔ transitioning → closing → ended`. Death, respawn and dimension transitions suspend virtual dispatch and revoke existing leases while preserving the attachment when the original player remains. Restore readiness after the required world/UI transition. Grant one lease at a time. `native` reserves movement to native controls and `virtual` suspends competing native movement while delivering renderer input. `ReleaseLease`, transfer out of ready, and termination clear held controls and queued stale input. `Detach` preserves the native actor. Player removal, GameTest completion, transport disconnect, and BDS shutdown publish terminal reasons and release session resources. Retain terminal state for event and artifact inspection; input and mutation against an ended generation fail.
- Inputs use the `InputCommand` union. A missing press tick count means one server tick. Presses and acknowledgements use server tick boundaries and may be cancelled by lease loss. The registry contains the only accepted action keys. The script-only `Input.TypeId` and individual unique action symbols are reconstructed by the pure input API; wire messages contain key strings. Bindings resolve actions to ordered raw inputs. Held input tracks the actual raw binding from hold until release, and `ReleaseAll` clears all controls for its session.
- The host sends `SyncSession` to its renderer before dispatching virtual input and whenever the bridge changes readiness or revokes the lease. The renderer clears held controls on either change and checks the lease again when executing queued input. Only the host may send this operation. Registry-key failures for recognized input shapes return `UnknownAction`.

## Clocks, media, and observation ports

- A host owns the session monotonic origin. Translate bridge and renderer times into that domain at the adapters and retain the optional originating server tick. `FrameTime.index` increases over completed frames for the session. `mediaPtsUs` describes media timing separately from the observation clock. A live BDS session uses real time. A controlled session with the `FixedClock` capability can explicitly request fixed-clock capture. Use PNG, MP4/H.264 and 60 FPS when options are omitted.
- The frame provider takes `FrameRequest` and returns each `FrameDescriptor` with its frame bytes in offset order, or a bounded `Failure`. Select the first completed frame strictly after `receivedAtMs + offsetMs`. `receivedAtMs` is when the observation reaches the renderer. Preserve `observed` and the completed frame time in the result. RGBA/BGRA rows contain four bytes per pixel and include stride padding. An optional audio stream supplies `AudioDescriptor` plus interleaved little-endian 32-bit float samples on the same clock. Media bytes go through an owned local stream or immutable handle with caller-scoped lifetime. Use JSON for descriptors and results. Every accepted frame or audio handle must be released exactly once.
- The capture engine takes session-bound screenshots and videos or the resolved `CapturePlan`. A screenshot returns a `CaptureJob` and publishes one `Artifact` per requested frame. Associate them using `jobId`. A started video returns `Recording`; use its ID as `jobId`. `StopVideo` returns the result after finalization. Publish completion through `Artifact` events and the run manifest, including every failed or interrupted output. A recognized output collision fails without overwriting. An encoder failure or incomplete/playability check produces a failed or interrupted artifact.
- The retention provider accepts `EnableLookBack`, `DisableLookBack`, and status reads. A new session begins disabled. The default is 10,000 ms with screenshot history enabled and video history disabled. A fresh enable increments `epoch` and starts empty. The provider exposes a coherent `HistoryIndex` with ordered frame timestamps, segment IDs, keyframe context, and availability. A `HistoryRequest` pins the specified interval and required decode dependencies. `HistoryPin` transfers a read lease for owned segment data to the export engine, which releases it on success, failure, or cancellation. Disabling retires unpinned data and preserves accepted pins until release. Bound temporary storage and concurrency and use explicit failures when over budget. Clean stale temporary data on startup. Historical PNGs identify `videoDerived` as their source.
- `Observation` carries timestamped named scalar facts from player, world, inventory, HUD, UI, and scripts. `Fact.subject` distinguishes named slots, entities, or other occurrences within a named fact. Keys are `(source, name, subject)` and are unique within a snapshot. `PublishFact` sends script facts or structured predicate errors; executable predicates stay in QuickJS. Unavailable facts may be omitted; an explicit `null` is an available scalar. Conditions compare same-type values, and ordered operators require comparable numeric or string facts. Missing facts make comparisons false. `exists` checks presence.
- Feed `TriggerEvaluation` to the pure trigger engine. It returns `TriggerDecision` with the next state, an optional activation plan, or a predicate failure. Initial true fires once. False re-arms the rising edge. Sustained true produces no new occurrences. `oncePerRun` and cooldown gate a rising edge. Predicate failure disables the affected trigger and fails the run. Registration, reset, enable, disable, and removal remain explicit. `ResetTrigger` clears the occurrence state and publishes a fresh state. Keep artifact and warning identities unique within a run, including after reset.
- Assign `nextActivation` from a counter scoped to the run, session, and trigger name. Advance it on activation and retain it across reset or re-registration to keep path and warning IDs distinct. `TriggerState.activations` counts activations since the last reset.
- A trigger override of `false` disables history for that trigger. An object inherits omitted fields from the session's enabled policy. An explicitly historical request against a disabled buffer yields `LookBackDisabled`. At activation, clamp requested history first to retention and then to availability. Sample the latest frame at or before the requested historical instant, or the earliest frame when there is no predecessor. Historical screenshot sequence offsets are relative to the selected instant. When screenshot history is requested without a screenshot action, synthesize one using trigger output defaults. Missing history never becomes a current screenshot. Historical video either exports through activation or prepends the interval to post-trigger media. A conditional post-trigger deadline is wall-clock time from activation. `WarningDelivery` is unique per run/session/trigger occurrence, reason, and sink. Send each reason once at activation to host console and structured MCP, plus BDS console for script-owned triggers. Retention clamping and unavailable or shortened history have distinct reasons.
- Artifact paths resolve on the rendering host against the run working directory. Expand only `runId`, `playerId`, `trigger`, `activation`, `index`, `tick`, `timestamp`, and `ext` tokens. Use `DefaultArtifactTemplate` when neither a name nor a template is provided. Apply explicit filename/template and directory settings first, then trigger output defaults. Require paths to stay within the selected directory after expansion, including case aliases and reparse points. Reject unsafe values, incompatible settings, and colliding outputs before creating a file. Return absolute host paths, observation/activation and media times, look-back durations, warnings, dropped-frame counts, and terminal completion. Persist the manifest under the owning run and flush it during orderly shutdown.

## Setup and ownership

- `BundleManifest` describes the complete owned install. Each entry is relative to the install root, slash-delimited, case-insensitively unique on Windows, and hash- and byte-count-verified. Reject traversal, device names, alternate streams, drive/UNC-qualified entries, ambiguous names, and reparse-point escape. A complete bundle independently requires all configured client, MCP, Go core, helper, asset, bridge/loader and license files. A manifest listing only some files cannot establish completeness. Provenance hashes cover the current local source and all pins. Preserve unrelated contents, stage and atomically publish only owned files, and retain enough state to recover a previous working install.
- `ProvisioningReceipt` binds an explicitly selected stopped BDS instance or MCP configuration to the bundle and to measured config/artifact hashes. It is an ownership receipt. Keep endpoint credentials separately in private configuration. BDS provisioning must verify process ownership, stopped status and the exact version tuple first. MCP provisioning records the installed executable/configuration, preserves unrelated entries, and uses the provisioner handshake against the installed endpoint.
- Setup adapters implement the existing [`BuildInstall`, `Provisioning`, `Currency` and `Processes` Effect services](../../../../Script/Setup/Source/Contract.ts). `Currency.inspect` combines manifest inputs/pins and freshly measured digests with the existing `Verification` fields. Use independent required-file discovery, measured provenance/ownership hashes, and per-target provisioning measurements. `BundleFixture.mjs` supplies deterministic file bytes, manifest, and provisioned file records. The [setup service fixture](../../../../Script/Setup/Test/Fixture.mts) replaces process, permission, and staging side effects in component tests. `--update` keeps its existing forced-current-local-build meaning.

The `Bedform-8ww.13` assignee owns shared changes until a successor is explicitly recorded in that issue. Component owners request a contract revision there before editing shared files. A revision updates the canonical schema, regenerated bindings, portable vectors, affected fixtures, and version policy together. Incompatible wire/document changes require a new major contract revision. The `Peers.mjs` native, renderer, and deterministic frame/index fixtures exercise the contracts independently of the production renderer, bridge, and encoder.

Work in separate component worktrees with isolated outputs, including per-worktree Cargo target and build directories. Use the measured memory and free disk to bound native build jobs. Serialize any use of the package runner's fixed `dist/bds-runtime/bedrock_server.exe` and any shared installation destination. Run fixed-path native checks in the native integration lanes with their existing firewall setup. This contract gate uses host peers and fixtures and claims schema, serialization, and component boundary conformance.

From the repository root, with Node 24.19.0 and the repository dependencies:

```powershell
node Package/ServerGameTest/Tool/AutomationContract.mjs --check
node --test Package/Cinnabar/Bedform/Contract/Contract.test.mjs
npm run typecheck --workspace @bedform/server-gametest
npm run lint --workspace @bedform/server-gametest
```

From `Package/Cinnabar/core`, run `go test ./internal/automationcontract`. The Rust fixture runs with `cargo run --locked --manifest-path Package/Cinnabar/Bedform/Contract/RustFixture/Cargo.toml` from the root, with the fixture target and build directories pointed at scratch paths. From an x64 Visual Studio Developer Command Prompt in a scratch directory, compile `NativeFixture.cpp` with `cl /std:c++20 /EHsc /W4 /WX /DNOMINMAX <absolute path to NativeFixture.cpp> /link windowsapp.lib` and run `NativeFixture.exe <absolute path to vectors.json>`. The fixtures use the same vector file, including 64-bit identities and recognized versus unknown action keys.
