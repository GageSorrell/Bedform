# Look Input Demo

The separate [entity Use qualification report](Documentation/ToggleCapture.md)
documents the unqualified `b2bb.1` bridge, isolated native reproduction, and physical
mouse/controller recorder. Run `npm run test:toggle --workspace @sorrell/look-input-demo`
for its native diagnostics. This does not change the normal item's toggle behavior.

Version 1.0.12 restores the pitch and yaw captured when the item was enabled. OFF sends a same-position rotation correction before clearing the external camera, so the character camera resumes facing the original direction. The saved rotation is separate from the changing look-measurement/recentering state. Position remains at the exit location. Cleanup without an active session does not change rotation. Native checks exercise repeated Use toggles, nine starting directions, a changed exit position and repeated cleanup; smooth visual handoff still requires client confirmation.

Version 1.0.11 removes the hard-coded FOV. Activation now runs `execute as @s at @s anchored eyes run camera @s set look_demo:first_person_snapshot pos ^ ^ ^ rot ~ ~` after stopping movement and correcting the player's position. Bedrock resolves the full native eye position and rotation together, replacing the script's mixed player-X/Z and head-Y snapshot. There is no authored height, forward offset, numeric FOV or delayed handoff. OFF still clears any FOV override left by an older demo. The 1.0.10 client-side head/flash guard is retained. This is a different engine anchoring path, not proof that server-side eyes equal every client-interpolated first-person frame; visual alignment remains an open client check. The older version notes below describe superseded implementations.

Version 1.0.10 guards first-person selection directly in both render-controller expressions and pre-animation. In the local world view, a camera within 2 blocks of the player root selects the head-hidden first-person presentation even if the synchronized active property has not arrived yet. This covers the activation/deactivation packet race and render-before-animation ordering without a delay, fade or blank frame. Other viewers and inventory/map previews retain native selection. A collision-clipped third-person camera within that radius also uses first-person presentation to avoid showing the inside of the player's head. The FOV remains 100°. Host regressions cover stale property values, selection before/after animation, standing/crouching-height distances, previews, spectator selection, and normal distant cameras. Client confirmation of the one-frame flash fix is still required. The distance is evaluated locally through [query.distance_from_camera](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/molangreference/examples/molangconcepts/queryfunctions?view=minecraft-bedrock-stable).

Version 1.0.9 explicitly uses **100° FOV**, matching the user's reported Video setting. Stable script APIs expose a FOV setter but no getter for the client's setting, so `CameraFieldOfView` in `Script/Camera.ts` must match that setting; it is not automatically detected. OFF removes the override. The snapshot preset retains player rendering effects and the player audio listener. The resource pack now selects vanilla first-person animation and render controllers for the active local world view, preserving the hand/item pose instead of suppressing that pass and leaving a world-space held item. The vanilla first-person controller hides the body and head. Other viewers, OFF state and previews retain native selection. The screenshot pair showed a roughly 20% scene magnification with a nearly unchanged horizon, consistent with a projection change; changing eye height again would not correct that. These presentation changes require a new physical-client before/after check; host controller checks and BDS cannot establish rendered pixel alignment. The older version notes below describe previous implementations.

An isolated Creative/Peaceful world for release BDS 1.26.63.1. The server supplies the custom add-on and resource pack. The existing `C:/MineCraft/Server` installation is used only as an engine source; its worlds and configuration are untouched.

From the monorepo root, launch:

```powershell
npm run demo:look-input --workspace @sorrell/look-input-demo
```

Connect to `127.0.0.1`, port `19132` (or the LAN address printed by the launcher), and accept the resource pack. Select **Look Input Toggle**, use first-person view, and tap Use. The view stays at the eye position and orientation captured at activation. Move the mouse or right stick and watch the action bar. Tap Use again to restore normal rendering and movement. New arrivals and respawns receive the item if they do not already have one. The item starts OFF.

Version 1.0.8 removes the unvalidated 0.10-block lift introduced in 1.0.5. The frozen camera uses the native head/eye anchor's Y coordinate and the player's centered X/Z coordinates, avoiding any horizontal head-component displacement. Its position is captured once at activation. Local-avatar hiding from 1.0.7 is retained. Host regression checks cover horizontal head offsets in four directions, multiple pose heights, and snapshot independence from later movement. Native anchor checks establish script coordinates; matching the rendered first-person viewpoint still requires a physical client check. View bobbing and client camera interpolation can differ from a server-side snapshot.

Version 1.0.8 displays `Rotation delta (yaw, pitch): (0.529 °, -0.281 °)/tick` on the action bar, updated every tick while ON. Both values are signed degrees per tick, truncated toward zero to exactly three fractional digits. Horizontal is yaw; positive vertical is downward pitch. The fixed camera is set once, `minecraft:body_rotation_blocked` is enabled through a player component group, and translation input permission is disabled. Camera input permission remains enabled. Activation also clears existing velocity and sends a same-position teleport to stop coasting and correct client movement prediction. OFF clears the external camera and restores the previous movement/camera permissions without changing player rotation. Respawn, reconnect and dimension changes clean up active sessions.

This is a rotation-derived look measurement. Neither the release-compatible stable 2.10.0 nor beta 2.12.0 typings expose `Input.getLookDelta` or another raw look-axis getter. `Player.getViewDirection()` returns the entity's current direction; `getRotation()` supplies the pitch/yaw representation used here. Each tick measures the change from the previous player rotation. At pitch greater than or equal to +85 degrees or less than or equal to -85 degrees, the add-on sends a same-position teleport with pitch zero and the current yaw. Starting in 1.0.3, yaw is also recentered to the activation yaw when its shortest signed angular offset reaches +45 or -45 degrees; yaw corrections preserve current pitch unless pitch also needs correction. The origin is captured anew each time the item is enabled. Version 1.0.7 replaces the earlier vanilla-controller head patch with an explicitly emitted player client entity. Its render-controller selection switches to `controller.render.look_demo.hidden` for the active local world avatar and disables all normal avatar controllers for that view. The custom controller hides every part, avoiding skin-bone naming assumptions. OFF state, other viewers, inventory and map previews keep their original rendering. This addresses self-head obstruction separately from camera coordinates; client visual verification is still required. Player teleportation does not support the `keepVelocity` option; a correction may clear velocity. It does not call `setRotation()`. Version 1.0.6 reconstructs correction gaps using a weighted average of the three preceding measured deltas for each axis. Values inferred during a reset or its recovery are prefixed with `≈` on the action bar. Pitch recovery is observed within 45 degrees and yaw recovery within 22.5 degrees of its activation origin. The corrected axis retains its pre-wrap velocity through stale packets and the acknowledgment rather than reporting zero or the teleport jump. A six-tick recovery window holds that estimate through the first three low samples, then blends back to measured values over three ticks; convergence or a measured direction reversal resumes direct measurement immediately. Unacknowledged estimates hold for eight ticks and decay to zero by sixteen ticks, including across teleport retries. This deliberately trades a short release-detection lag for continuous drag estimates; raw device input during the correction cannot be recovered exactly. Unconfirmed corrections are retried after ten ticks, avoiding per-tick correction spam. Versions through 1.0.1 used `setRotation()`, which the real-client test reported leaving pitch stuck at 89.9999 degrees. The teleport change still requires real-client acceptance. The external camera does not follow that recentering. Device sensitivity, client/server timing and recenter corrections can affect these measurements. Actual mouse/controller behavior remains a client acceptance check. Third-person cameras, view bobbing and FOV effects are not captured by this eye-pose snapshot.

Validation on release BDS 1.26.63.1 (build 53340801): native simulated-player spawn supplies the item; default OFF; four native Use events alternate ON/OFF; look permission stays enabled; movement restores; ordinary rotation is retained; pitch/yaw teleports occur only at their limits and preserve position and the other axis; the item is retained; walk/sprint activation clears existing velocity and shows no coasting over the next five ticks; the synchronized head-visibility property restores on OFF. `dist/native-probe.log` records the passing run. Eleven host tests verify signed truncation, negative zero, yaw wrapping, delayed/stale correction samples in both pitch directions and bounded retries, yaw limits across the world-angle seam, independent recovery after simultaneous pitch/yaw corrections, explicit local-avatar controller selection with normal OFF/remote/inventory behavior, constant-speed yaw/pitch traces through stale and ramping reset samples, and bounded estimates after release or failed acknowledgments. Simulated rotations validate the script loop, not physical mouse processing or client rendering. A client test of the original version reported visible body rotation despite the component; that behavior remains an open investigation.

The demo world is stored at `Demonstration/look-input/server/worlds/look-input`. Stop the server with `stop` in its console or Ctrl+C. Rebuilding and replacing the demo with `demo:prepare` creates a full sibling backup of its predecessor. Ordinary launch preserves the world. Native probes use disposable worlds at the fixed `Addon/LookInputDemo/dist/bds-runtime/bedrock_server.exe` path, with isolated pack identities and GameTest configuration. They do not replace the playable demo's scripts, configuration or world. The playable demo requires no experiments.

```powershell
npm run typecheck --workspace @sorrell/look-input-demo
npm run lint --workspace @sorrell/look-input-demo
npm test --workspace @sorrell/look-input-demo
npm run test:native --workspace @sorrell/look-input-demo
```

Run only one probe at a time because the probes share their fixed runtime path. `npm run test:diagetic --workspace @sorrell/look-input-demo` exercises Bedform sessions with scripted observations and the common presentation packs; it does not qualify physical entity Use. For LAN firewall setup, `npm run firewall:configure` is the repository's explicit administrator setup command. Demo creation, probes and normal launch never elevate.

`npm run test:diagetic:persistence --workspace @sorrell/look-input-demo` saves controls with an active grab, stops the isolated server and reopens the same world in a fresh process. It checks scalar/pose/binding restoration, all six face frames, inactive restored motion, ordinary block-state changes and support replacement. The two process logs and JSON results are written under `dist/diagetic-persistence*`.
