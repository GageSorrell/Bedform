# Bedform custom rigid-body physics

## Summary

Add an Effect-style physics API, a custom Bedrock entity runtime, and a CLI asset compiler. Each `PhysicsEntity` represents one rigid body with one custom model, rendered either as a collection of cuboids or as particles created by Bedform CLI-generated code. It may manage pooled invisible entities to support interaction with players and mobs.

Particle authoring, generated rendering code, textures, and pack assets follow [Blender models rendered with Bedform particles](Bedform_CustomModels_Grabbing_Plan.md). Particle models derive their physical geometry from the evaluated Blender mesh, independently of how its faces are merged or textured for rendering. Deprecated `poly_mesh` models are unsupported.

Both representations use one common visual root bone whose position and rotation offsets are interpolated over the 50 ms between physics ticks. Reuse a suitable existing root and preserve authored descendant bones; add a trivial root when the representation would otherwise have no bones.

Support boxes, capsules, spheres, ellipsoids, compound shapes, and geometry-matching complex collision. Bodies collide with each other, Minecraft terrain, players, and vanilla mobs. They persist through saves, restarts, and chunk unloading.

Physics implementation depends on the completed math epic, `MineCraft-ner`. The physics epic, `MineCraft-8zu`, defines and implements mesh-solid compilation and renderer-attachment contracts; the subsequent custom-model epic, `MineCraft-2zx`, implements Blender export and particle rendering against those contracts. Do not add a reverse dependency from physics to the particle epic.

## Public API and physical behavior

- Add pure root namespace exports and matching subpaths for `CollisionShape`, `PhysicsEntity`, and `PhysicsWorld`. Add explicit runtime integration at `bedform/PhysicsRuntime`; root imports must remain free of Bedrock runtime imports and subscriptions.
- Follow the math modules’ conventions: immutable public values, functional operations, `dual` receiver overloads, Effect protocols where applicable, `Result` for validation failures, and `Option` for absent results. Use `effect-bedrock`; upstream Effect remains confined to the CLI.
- Provide constructors, state inspection, pose/property updates, force and torque application, impulses at world points, velocity updates, and body removal. Expose ordered contact-begin/contact-end events and typed diagnostics.
- Support dynamic, static, and caller-driven kinematic bodies. Kinematic movement contributes contact velocity but is unaffected by impulses.
- Use the math epic’s coordinate conventions. Positions are in blocks, time in seconds, mass in kilograms, linear velocity in blocks/second, and world-space angular velocity in radians/second. Linear velocity describes COM motion; the public pose describes the model origin.
- Reuse the math epic's `Transform` (position/quaternion, no scale), `RigidTransform` (pose plus origin velocity and angular velocity), `Plane`, `AABB`, `OBB`, `Ray`, and solid-3D `ConvexHull` throughout public state, compilation and static queries instead of introducing duplicate structural geometry types. Model-origin visual endpoints are `Transform` values. Motion-bearing snapshots exposed as `RigidTransform` carry origin velocity, not COM velocity.
- Keep COM linear velocity authoritative inside the solver. At the public boundary compute `vOrigin = vCOM + cross(angularVelocity, origin - COM)`; convert back with `vCOM = vOrigin + cross(angularVelocity, COM - origin)`. Both use world-space vectors and radians/second angular velocity. Renderer endpoint extraction discards velocities and must not introduce velocity-driven interpolation or change the fixed 50 ms presentation contract.
- Use shared planes, boxes, hulls and unit-direction rays for compilation, broad-phase bounds, convex-cell geometry and static queries. Preserve source object/face references, cavity topology and internal partition-face suppression as physics metadata alongside the generic math values. Hull construction is not a concave decomposition or an allowed fallback approximation. GJK/EPA contact solving/manifolds, continuous collision detection, AABB-tree maintenance and dynamics remain physics responsibilities.
- Model registrations distinguish cuboid rendering from CLI-generated particle rendering and carry versioned physical-geometry metadata. Define a renderer-neutral attachment contract for committed start/end model-origin poses, the 50 ms interpolation duration, sequence/reset markers, render-base information, and lifecycle notifications without importing `ParticleRuntime` into the pure API or making physics depend on that renderer. Generated particle descriptors and typed spawn helpers consume this contract through explicit runtime integration.

Physical properties:

| Property | Contract |
|---|---|
| Mass/density | Mutually exclusive inputs, enforced by types and runtime validation. Default mass is 1 kg; density uses the cuboid union's or Blender mesh solid's volume. |
| COM | Defaults to the uniform-density solid-volume centroid, including the effect of mesh cavities. An override is expressed in model-local coordinates. |
| Inertia | Derived from the cuboid union or Blender mesh solid and selected COM, independently of collision approximation, particle count, texture alpha, or masked face regions. |
| Restitution | Finite value from 0 to 1; default 0. Contacts use the larger participant value. Terrain and native entities default to 0. |
| Friction | Fixed Coulomb coefficient of 0.5 for both static and sliding contact; no public customization. |
| Gravity | World default `(0, -9.81, 0)`, with per-body vector overrides. Also provide a magnitude/direction constructor; zero gravity is valid. |
| Initial velocities | Both default to zero and remain independently updateable. |

Configuration changes preserve the model’s world pose, rebuild affected mass properties, and wake the body. Reject nonfinite values, nonpositive mass/density, degenerate solids, and invalid orientations.

## Asset compilation and collision simulation

**CLI and geometry**

- Implement `bedform build --config bedform.config.json --out <directory>` as the physics asset compilation command. Configuration identifies the add-on namespace, pack roots, and model registrations, including rendering representation, cuboid geometry identifier and textures/materials or generated particle descriptor and mesh-solid metadata, collision selection, and physical defaults.
- Emit generated behavior/resource-pack overlays and a typed TypeScript model catalog for the consumer’s script build. Keep script bundling, installation, and `.mcaddon` packaging outside this command’s initial scope.
- Support rigid Bedrock cuboid geometry, including cube inflation, cube rotations, bone hierarchies, and authored bone transforms. Bake geometry at build time and preserve one rendered model per body.
- Support particle models produced by `bedform model particles <model.blend> --namespace <namespace> --out <directory> [--name <name>]`, as specified in the custom-model plan. That command generates the TypeScript descriptor and rendering code, behavior/resource-pack overlays, and generation report. Blender setup, resource resolution, per-face appearance, particle-region merging, and the fixed 4096x4096 mask ceiling remain governed by that plan.
- Define a versioned mesh-solid interchange contract consumed by the physics compiler and emitted by the later Blender exporter. It carries evaluated model-local vertices and oriented triangle topology, source object/face references for diagnostics, coordinate/unit metadata, and a geometry fingerprint. Preserve this physical geometry before coplanar particle-region merging, UV compositing, and texture masking; rendering changes must not alter its volume or collision surface.
- Reject deprecated `poly_mesh`, experimental texture meshes, and animated collision deformation with actionable diagnostics. Route arbitrary rigid Blender meshes through generated particle rendering rather than emitting a Bedrock mesh model.
- Convert model coordinates into the math epic’s world conventions exactly once. For Blender, use the custom-model plan's scene origin, one metre per block, and `(x, y, z) -> (x, z, -y)` conversion. Validate both sources with asymmetric models that expose axis signs, units, pivots, mirrored transforms, and rotation order.
- For cuboid models, compute the solid union of transformed cuboids. Partition overlapping geometry into nonoverlapping convex cells using plane clipping; calculate volume, centroid, and inertia from that partition.
- For particle models participating in physics, require closed, consistently oriented, non-self-intersecting manifold mesh solids with positive total volume. Support disconnected solids and properly enclosed cavities; reject intersecting or ambiguous shells, open boundaries, nonmanifold edges, degenerate faces, and invalid topology with source object/face diagnostics. Apply this solid requirement to physics registration; standalone particle rendering may still use valid open face regions under the custom-model plan.
- Calculate particle-model volume, centroid, and inertia from the validated mesh solid, subtracting cavity volumes. Build a volume-preserving decomposition into nonoverlapping convex cells for complex collision, preserving concavities, cavities, and openings within documented geometric tolerances. Bound validation and decomposition work explicitly and reject unsupported complexity or failed decomposition without silently substituting a hull or cuboid proxy.
- Complex collision uses the cuboid union or mesh-solid decomposition for dynamic and static bodies. Mark internal partition faces so they do not produce artificial contacts.
- Provide deterministic enclosing primitive fits, explicit primitive dimensions/local poses, and compound collider construction for both representations. Default collision is a model-local bounding box. Mass properties always come from the source solid, independently of the selected collider.
- Generate stable namespaced entity identifiers, helper definitions, common-root position/rotation interpolation animation, model fingerprints, and versioned catalog data. Reuse a suitable existing root; preserve authored bone hierarchies and fixed local transforms. Add a trivial root for a representation with no bones; if there are multiple authored top-level bones, retain them beneath one common root. The shared root applies the rigid visual pose, without introducing per-face animation or collision deformation. Fingerprints cover physical geometry and the compatible rendering descriptor/assets so restoration can detect incompatible generated output. Builds must be deterministic and clean only files recorded as their own generated output.

**Solver**

- Advance one 50 ms simulation tick using four fixed substeps. Use semi-implicit integration, quaternion orientation updates, full inertia tensors, and angular momentum.
- Use a dynamic AABB tree for body broad-phase queries and per-model acceleration structures for complex geometry.
- Implement analytic primitive cases where useful and support-mapped GJK/EPA with contact clipping for general convex pairs. Complex bodies dispatch against their convex cells, merge manifolds, and suppress internal seams.
- Resolve contacts with warm-started sequential impulses, ten velocity iterations per substep, penetration correction, restitution thresholds, and fixed friction. Include sleeping, contact-island waking, and swept continuous collision detection with angular-motion bounds.
- Keep deterministic ordering for identical inputs. Private mutable work buffers are permitted; published snapshots and caller inputs remain immutable.
- Bound geometric and solver work explicitly. Report unsupported complexity or convergence failure and pause the affected island; never silently replace complex collision with a hull or discard bodies.

## Bedrock integration and persistence

- Generate a persistent physics owner entity for each body, with native gravity and ordinary movement disabled. The owner renders the model for cuboid registrations and is invisible for particle registrations. Synchronize the visual pose through the common-root interpolation contract below and client-synchronized properties.
- Attach CLI-generated particle rendering through the explicit particle runtime and the physics renderer-attachment contract. Use the custom-model plan's one invisible, non-colliding anchor per renderer instance, separate from the persistent physics owner and pooled native-contact helpers. Its common root drives every face locator with the same interpolated pose. Rendering follows committed pose intervals without changing collision or mass properties; do not create an entity or animated bone for each face or convex cell.
- Start subscriptions and tick processing only through explicit runtime startup. Provide idempotent disposal, startup rollback, and isolated error reporting.
- Implement a terrain resolver for full cubes, slabs, stairs, fences/gates, walls, doors, trapdoors, snow layers, and common thin blocks. Resolve state-dependent orientations and connections. Unknown blocks use a reported conservative full-cube fallback; provide a resolver registration API for other add-ons.
- Re-read relevant block permutations each tick, sharing queries across bodies. Cache shape definitions by permutation rather than assuming all block changes produce observable events.
- Represent native entities using their reported AABBs and measured movement. Use a documented 80 kg effective bridge mass, locked angular response, and conversion between native tick velocity and physics units.
- Apply custom contact impulses and terrain-checked separation corrections while preserving native walking and jumping. Track support points in body-local coordinates to carry standing entities through translation and rotation; jumping or losing contact releases support.
- Pool small invisible support helpers near active native contacts. Custom collision remains authoritative; do not create one entity per triangle or convex cell. Verify helper component behavior before building the complete bridge: native collidable entities are documented as unreliable while moving. ([Collision limitation](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/entityreference/examples/entitycomponents/minecraftcomponent_is_collidable?view=minecraft-bedrock-stable))
- Persist versioned body state on the physics owner entity, including rendering representation/catalog reference, model fingerprint, physical overrides, pose, velocities, and sleeping state. Persist awake state after each committed tick and sleeping state when changed. Particle renderer instances and anchors remain transient.
- Restore through startup discovery and entity-load events. Pause bodies when required terrain is unloaded; resume without replaying elapsed unloaded time. Recreate attached particle rendering from compatible catalog data, recreate helpers from contacts, and remove orphaned anchors/helpers. Handle body removal, dimension changes, runtime disposal, unload/reload, and startup rollback with idempotent attachment cleanup.
- Retain and pause bodies whose saved schema, model fingerprint, or required generated rendering descriptor/assets are incompatible or unavailable, reporting a typed diagnostic instead of overwriting their state or silently switching representation.
- Centralize script-owned identifiers in exported frozen key records. Do not create ticking areas automatically.

### Visual interpolation between physics ticks

- Apply each body's visual translation and full rotation through offsets on one common root at the model origin, for both cuboids and particle locators. Preserve existing descendant bones and authored fixed transforms. A bone-less cuboid representation or particle-anchor geometry gets a trivial root; existing suitable roots are reused, with a common parent added only when multiple roots need grouping. The root pivot is the public model origin, while dynamics and grabbing continue to use the configured COM.
- At each committed 50 ms update, publish the previous pose as the visual start and the newly computed pose as the endpoint to reach by the end of the following 50 ms interval. Compute that endpoint through the existing four physics substeps before publishing it. This is interpolation between known states with one tick of visual buffering under normal delivery, not a second predictive simulation or an extrapolation of unknown future inputs. Authoritative collisions, contacts, ownership, spring/separation checks, and saved state use the committed physics pose, never the intermediate visual pose.
- Generate client animation/Molang that evaluates once per rendered frame. Use one shared linear progress value `alpha = clamp(elapsedSeconds / 0.05, 0, 1)` for position and rotation. Lerp model-origin position component by component. Lerp rotation using shortest-path normalized quaternion lerp: align the endpoint quaternion's sign to the start, linearly blend its components with the same alpha, normalize, then convert the result to the root bone's rotation convention. Resolve exact half-turn ties deterministically. Do not use easing, exponential chasing, or independent per-axis timers; ensure angle wrapping and equivalent `q`/`-q` endpoints cannot cause long spins or invalid rotations.
- Send complete start/end poses, a sequence/reset marker, and the render-base data through generated `client_sync` entity properties. Client `pre_animation` latches a coherent interval and resets elapsed time once for each new sequence; subsequent rendered frames advance it with `query.delta_time`. Duplicate/stale sequences must not restart interpolation or mix fields from different intervals. Clamp at the endpoint if no update arrives; never continue drifting. On skipped intervals, discard obsolete history and reset to the latest coherent pose instead of replaying a backlog. Validate endpoint publication and timing on the actual engine rather than assuming property writes arrive atomically or that a free-running animation loop aligns with script ticks. [Entity properties](https://learn.microsoft.com/en-us/minecraft/creator/documents/introductiontoentityproperties?view=minecraft-bedrock-stable), [per-frame animation](https://learn.microsoft.com/en-us/minecraft/creator/documents/animations/animationcontroller?view=minecraft-bedrock-stable), [Molang queries](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/molangreference/examples/molangconcepts/queryfunctions?view=minecraft-bedrock-stable)
- Keep the native visual entity's rotation neutral and express full orientation in the root. Calculate root translation offsets relative to the actual rendered owner/anchor origin, converting blocks to geometry units and applying the documented axis conventions. When native entity positions are updated or the base is rebased, compensate both endpoints so the resulting world-space visual pose stays continuous. Prove that native entity movement interpolation does not double-apply motion or introduce 20 Hz jumps; merely teleporting the entity each tick and animating uncompensated local offsets does not satisfy this contract.
- Cuboid bones inherit the root transform. Particle face locators attach directly to the same common root with their authored local positions/orientations; existing live particles and emitters must follow its per-frame translation and rotation, including roll. Do not smooth particle faces separately or smooth the cuboid and particle paths twice. Preserve the one-anchor particle lifecycle and rendering-independent physical properties. [Animated locators and attached emitters](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/particlesreference/particleentityintegration?view=minecraft-bedrock-stable)
- Treat interpolation history as transient presentation state. Initialize both endpoints to the current committed pose on spawn, late join, restoration, renderer recreation, explicit teleport/pose discontinuity, dimension change, or skipped-sequence reset. Clear old offsets/history on disposal and rollback. A paused/sleeping body settles at its last committed endpoint; ordinary grab, manual rotation, drop, and throw continue through the same interpolation stream without restarting it. Preserve the existing persistence and unavailable/incompatible-asset diagnostics.

## Validation and delivery

- Test every shape pairing, rotated and concave bodies, narrow openings, overlapping source cubes, internal seams, and continuous collision against thin obstacles.
- Add mesh-solid fixtures for analytic volume/centroid/inertia, concavity, enclosed cavities, disconnected solids, mirrored transforms, convex decomposition, and internal seam suppression. Reject open, nonmanifold, self-intersecting, ambiguously nested, degenerate, and over-budget meshes with source diagnostics. Verify that particle merging, mask resolution, UVs, and texture alpha do not change physical geometry or mass properties.
- Verify analytic mass/volume/inertia fixtures, COM overrides, custom gravity, off-center impulses, angular response, restitution, friction, stacking, sleeping, and momentum/energy behavior within documented numerical tolerances.
- Test immutable snapshots, both `dual` call styles, declaration inference, typed failures, clean packed consumers, and operation without Node/browser globals.
- Test deterministic CLI output, generated owner assets for both representations, stale-output cleanup, rejection of `poly_mesh`, versioned mesh-solid input, unsupported geometry diagnostics, and matching visual/collision coordinate transforms. Verify pure and packed consumers do not pull Blender, Node, or particle runtime imports into the physics data API.
- Add isolated BDS fixtures for terrain states, native pushing, standing, walking/jumping off moving or rotating bodies, visible and invisible physics owners, chunk unload/reload, helper cleanup, and actual process restart. Exercise the renderer-attachment contract with a test adapter during physics work, including committed poses, restoration, dimension changes, removal, rollback, missing/incompatible catalog assets, and repeated disposal.
- Test common-root generation for existing hierarchies, multiple roots, and bone-less representations; root-origin versus COM offsets; position and normalized quaternion lerp at 0, 12.5, 25, 37.5, and 50 ms; simultaneous translation/full rotation; angle wrapping, half-turn ties and equivalent quaternion signs; and endpoint clamping/reset/sequence handling at varied frame rates. Verify physics results are unchanged by visual interpolation. An early engine/client fixture must prove frame-by-frame root offsets, coherent property timing, render-base rebasing and absence of doubled native smoothing before completing the renderer integration. Real client captures must show intermediate cuboid poses between 20 Hz updates; downstream particle evidence must additionally prove existing particles follow interpolated root locators rather than jumping or only updating at emitter renewal.
- Benchmark 128 simultaneously active bodies: 96 primitives and 32 complex models of up to 32 authored cubes each, with terrain and native contacts. Target physics-runtime p95 below 15 ms per server tick on the documented test machine during a ten-minute run, with no watchdog termination. Also report an all-complex stress scene.
- Additionally benchmark representative mesh-solid fixtures, reporting source triangle count, convex-cell count, compile/decomposition cost, and physics-runtime timings. In the downstream particle integration, also report particle/anchor counts and sustained rendering behavior; retain the existing cuboid benchmark target.
- Require two-player client validation for cuboid orientation, synchronization, support jitter, jumping, and collision approximations. Under the subsequent custom-model epic, validate real CLI-generated particle models against their mesh-derived physics through full orientation, late joining, unload/reload, process restart, and disposal. Record real particle visual/lifecycle evidence and mesh/particle performance there; do not make completion of prerequisite physics depend on the downstream renderer. Treat missing client evidence or failed performance targets as outstanding acceptance work in the owning epic. The custom-model plan's 4096x4096 platform-support assumption and absence of an all-platform resolution qualification gate remain unchanged.
- Use a fixed `Package/Bedform/dist/bds-runtime/bedrock_server.exe` test runner and extend the repository’s firewall setup; ordinary tests must not elevate.
- Validate shared geometry imports and conversions, world-space COM/origin velocity round trips with offset COM and simultaneous rotation/translation, rigid-frame velocity transport, degenerate bounds, normalized-ray distance units and exact hull-based collision queries. Confirm visual endpoints remain pose-only Transform values and source-solid cavities/concavities are preserved.
- Track physics implementation in `MineCraft-8zu`, dependent on `MineCraft-ner`, with self-contained child work for compilation/contracts, collision, dynamics/public API, runtime/native interaction, and validation. Embed this specification in the epic and retain the relevant contracts and acceptance criteria in its descendants. Track Blender mesh-solid export and real particle rendering integration in the existing `MineCraft-2zx` descendants, which remain downstream of physics. Leave implementation issues open until their own implementation and validation are complete. Preserve unrelated edits and package versions; follow repository TSDoc and type conventions, including generators and generated code.

Rigid geometry is the initial boundary: joints, breakage, deformation, buoyancy, and fluid simulation are excluded. This plan performs no implementation, deployment, commits, pushes, or remote synchronization.

### Success Criteria

The functional physics API, compiler, solver and runtime meet the behavior and validation requirements above, reuse the shared spatial math types, preserve COM-based authoritative dynamics through explicit origin-velocity conversions, and retain the common-root 50 ms visual contract. Source concavities, cavities and provenance survive the shared hull representation. Implementation remains incomplete until the owning issues have their required host, engine, performance and client evidence.
